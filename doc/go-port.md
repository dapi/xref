# Go-порт для Ruby/Rails

Это ранняя Go-реализация ядра xref. Исходный Ruby-движок и [спецификация](guide.md)
сохранены в форке как эталон. Автор исходной идеи и спецификации —
[Nik Grebnev](https://github.com/nikgrebnev), исходный проект —
[nikgrebnev/xref](https://github.com/nikgrebnev/xref);
условия использования находятся в [LICENSE](../LICENSE) и
[LICENSE-docs](../LICENSE-docs).

Go-порт строит локальный индекс Ruby-кода, Ruby-вставок в ERB/Haml и дампа
`db/structure.sql`. Он
использует Tree-sitter для Ruby и парсер PostgreSQL для SQL. Индекс лежит в
пользовательском каталоге кэша за пределами анализируемого проекта. Код и
содержимое БД никуда не отправляются. Для сборки нужен Go и C toolchain,
поскольку оба парсера используют cgo.

## Сборка и запуск

Из корня этого форка:

```sh
go build -o bin/xref-go ./cmd/xref-go
```

Из корня анализируемого Ruby-проекта:

```sh
~/code/xref/bin/xref-go refresh
~/code/xref/bin/xref-go where products.id
~/code/xref/bin/xref-go find 'Product.where'
~/code/xref/bin/xref-go blind
~/code/xref/bin/xref-go audit
~/code/xref/bin/xref-go route 'GET /orders'
~/code/xref/bin/xref-go trace orders.status
~/code/xref/bin/xref-go callers app/services/order_lookup.rb
```

Если дамп схемы находится в другом месте, передайте `--schema repo=путь` до
команды. Несколько источников позволяют сравнить схемы:

```sh
~/code/xref/bin/xref-go --schema stage=/path/to/stage.sql \
  --schema prod=/path/to/prod.sql drift
```

Живую схему PostgreSQL можно читать через установленный `psql`. Источник
`pg:STAGE` берёт параметры подключения из `XREF_STAGE_PGHOST`,
`XREF_STAGE_PGPORT` (по умолчанию 5432), `XREF_STAGE_PGDATABASE`,
`XREF_STAGE_PGUSER`, `XREF_STAGE_PGPASSWORD` и необязательного
`XREF_STAGE_PGSSLMODE`. Пароль загружайте из `pass` в окружение процесса:

```sh
XREF_STAGE_PGHOST=localhost XREF_STAGE_PGDATABASE=my_app \
XREF_STAGE_PGUSER=reader XREF_STAGE_PGPASSWORD="$(pass show your/pass/entry)" \
~/code/xref/bin/xref-go --schema repo=db/structure.sql \
  --schema stage=pg:STAGE drift
```

Имена источников (`STAGE`, `PROD`) позволяют сравнивать несколько подключений.
Запрос читает только каталог `public`, сессия принудительно работает в режиме
read-only. Соединение обновляется при каждом вызове; если оно недоступно, команда
завершается ошибкой вместо использования устаревшей схемы. Пароль и строка
подключения не сохраняются в индексе и не передаются в аргументах `psql`.

`--project` задаёт корень проекта, `--json` выводит машинный результат,
`--limit` ограничивает печать строк. `blind` исключает тестовые файлы по
умолчанию; `--include-tests` включает их. Короткий текст `find` ищется буквально
без учёта регистра. Поле `file_tables` в JSON означает таблицы, найденные где-то
в файле, а не на строке совпадения.

## Что уже работает

- `where`: обращения к таблице или колонке в разобранном SQL и распознанных
  вызовах ActiveRecord; уровень достоверности показан у каждой записи.
- `find`: поиск по текстовым файлам проекта с отметкой, проиндексирован ли файл.
- `blind`: возможные обращения к таблицам, отсутствующим в выбранном дампе.
- `drift`: различия таблиц и колонок между двумя или более источниками схемы.
- `audit`: объём индекса и его наблюдаемые пробелы.
- В `app/models` распознаются Rails `scope :имя, -> { ... }` с буквальным
  именем на модели с известной таблицей. Вызов `Product.common` ведёт к
  обращению к таблице и колонкам внутри lambda. Это статическая связь:
  уровень достоверности для таблицы — `inferred` или `candidate`.
  Scope из `app/models/concerns` внутри `included do` связывается с моделью,
  если в ней есть явный `include` этого модуля. Продолжение цепочки
  `Product.common.published` разрешается, когда предыдущие вызовы однозначно
  являются scope или известными операциями, возвращающими relation.
- `route`: статические цепочки от Rails-маршрута к действию контроллера,
  вызову метода и обращению к таблице. Можно передать путь или `VERB /путь`.
  Обычный шаблон действия ERB/Haml связывается с маршрутом по соглашению Rails.
  Литеральные `render :action`, `render 'action'`, `render template: 'path'`
  и `render partial: 'path'` добавляют явную связь с шаблоном. В ответе
  `gaps` показывают неподтверждённые переходы: динамический вызов или render,
  отсутствующий метод или шаблон, ответ без шаблона и переход через redirect.
  Это объяснение границ
  индекса, а не доказательство ошибки приложения.
- `trace`: такие же цепочки для таблицы или колонки. Показывает только найденные
  цепочки; отсутствие цепочки не означает, что обращение недостижимо.
- `callers`: распознанные вызовы методов указанного файла и маршруты к его
  контроллеру или шаблону. Путь задаётся относительно корня проекта.
- Для маршрутов разбираются прямые `get`/`post`/`put`/`patch`/`delete`/`root`
  с явной целью `controller#action`,
  `resources`/`resource`, `scope`, `namespace` и обычные вложения `member` и
  `collection`. Записи маршрутов и связи вызовов имеют уровень `candidate`:
  наличие синтаксиса подтверждено, но фактический dispatch Rails и Ruby не
  проверен. Вызов через локальную переменную связывается с методом только при
  единственном прямом присваивании `query = ItemsQuery.new` или
  `klass = ItemsQuery` внутри того же метода. Присваивания в ветках и повторные
  присваивания оставляют пробел в цепочке.
- Интерполяции в SQL отмечаются отдельными `sql_hole` со строкой и позицией.
  Индекс различает подстановки значения, имени таблицы, фрагмента выражения и
  подстановки внутри идентификатора. Динамическое имя не превращается в
  вымышленную таблицу; такие запросы остаются слепой зоной `sql_blind`.
  `audit.sql_hole_contexts` показывает распределение этих случаев.
- ERB: Ruby-теги `<% … %>` и `<%= … %>`; Haml: строки `=`/`-`, выражения после
  тега (`%span= …`), Ruby-хеши атрибутов `{…}` и интерполяции `#{…}`.
  Найденные обращения сохраняют строку исходного шаблона. `audit` показывает
  число шаблонов, извлечённых Ruby-фрагментов и ошибок границ фрагментов.
- Пересканирование изменённых файлов перед каждой командой. Изменение бинарника
  или схемы вызывает полное пересканирование.

## Границы этой версии

Это **не функциональный эквивалент** исходного xref. Команды `route`, `trace`
и `callers` читают файлы и локальный индекс: они не запускают Rails и не
подключаются к базе данных. `db/structure.sql` при наличии читается как файл;
`--schema имя=pg:ИСТОЧНИК` остаётся отдельной явной возможностью для сверки
живой схемы и не нужен для трассировки. Живые источники не подключаются
повторно по умолчанию после предыдущего запуска: флаг `--schema ...=pg:...`
нужно передавать каждый раз, когда требуется чтение PostgreSQL.

Статический разбор маршрутов
не исполняет `draw`, constraints, concerns, redirects, custom actions и
динамические условия; его вывод нельзя считать полным `rails routes`.
Связь с обычным шаблоном предполагает стандартный render; частичные шаблоны
отслеживаются только при явном литеральном `render partial:`. Условия веток,
кастомные рендереры и динамические имена шаблонов не выполняются.
Цепочки вызовов охватывают
однозначные вызовы `Class.method`, `Class.new.method`, `Class.new` →
`initialize`, `self.method`, прямые вызовы через однозначную локальную
переменную, статически объявленные Rails scope (в том числе из явно
подключённых concerns), цепочки relation и методы того же класса.
Они не знают о наследовании, callbacks и runtime dispatch.
Ruby-метапрограммирование,
модели в переменных при сложном потоке данных, сложные правила инфлексии,
SQL-фрагменты, полный синтаксис
ERB/Haml, шаблоны Slim, production-логи и остальные команды исходника пока не
поддерживаются. `audit` сообщает количество разобранных файлов, ошибок Ruby,
неразобранного SQL и неподдерживаемых шаблонов. Извлечение Ruby из ERB/Haml не
является полноценным компилятором шаблонов: нестандартные конструкции могут
остаться невидимыми даже когда файл проиндексирован. `blind` по модели, имя
таблицы которой выведено по соглашению Rails, является кандидатом для ручной
проверки.

Связь с concern учитывает только явный `include` в классе модели и scope с
буквальным именем и встроенной lambda в `included do`. Косвенные включения,
переопределения scope, произвольные методы relation и выполнение Ruby не
разрешаются. В concern колонки за вызовом другого scope отмечаются как
`candidate` и показываются только когда этот scope тоже найден у модели.

Перед использованием результата для изменения БД проверьте конкретную находку
по исходному файлу и фактической схеме нужного окружения.
